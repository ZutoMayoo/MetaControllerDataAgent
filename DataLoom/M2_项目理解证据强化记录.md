# M2 项目理解证据强化记录

日期：2026-09-22

## 目标

阻止仅由测试注释、界面配置或宽泛自然语言支撑的核心业务规则进入 SQL 生成阶段，同时保持项目无关、Benchmark 无关和 Gold 隔离。

## 设计

- EvidencePackage `0.2` 为每条规则增加 `CORE` / `SUPPORTING` 关键性标记。
- 每个来源分别声明材料类型及其支持用途；核心规则至少需要一条直接参与决策的生产代码证据。
- 核心规则使用 `decision_semantics` 区分主体、既有状态、配置和上下文输入，并明确谓词与边界行为。
- `readiness` 由宿主控制器根据合同确定性计算，模型不能自行把不完整证据声明为可交付。
- SQL Bridge 只接受状态为 `READY` 的 0.2 EvidencePackage。
- 0.1 历史产物继续允许做来源审计，但不能重新进入 0.2 SQL 推理链。
- Project Understanding 运行器支持显式注入一个或多个 Skill，并在审计日志中记录 Skill 路径和 SHA-256。

## 风险控制

- Skill 和提示词不包含具体项目、函数、字段、任务标识或已知答案。
- 测试使用独立合成规则，不复现开发集任务。
- 测试、UI 和文档可以作为检索线索或行为示例，但不能单独满足生产决策门禁。
- 明显的测试文件路径即使被错误标成生产代码，也会被合同验证器拒绝。
- 无法找到生产决策点时保留 `INCOMPLETE` 产物，不允许用常识或评测反馈补齐。

## 验收

- 生产决策证据齐全的合成包可进入下游。
- 仅有测试证据的核心规则被保留并标记为不完整。
- 模型伪造 `READY` 状态会被拒绝。
- 测试路径伪装为生产决策证据会被拒绝。
- 0.1 历史包仍可验证，但不能进入新 SQL 链路。
